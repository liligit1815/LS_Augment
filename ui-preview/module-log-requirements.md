# 模块日志导出要求（待布局确认后实现）

本轮只实现网页 UI 与可下载的结构示例；未修改 Android 日志采集器。本文件记录用户要求及依据，不能视为手机功能已经实现。

## 当前代码核查

- FeatureActivity.diagnosticSummary：包含模块与设备版本、Root、目标包版本、配置运行镜像、SharedPreferences 中的 Hook 诊断键。
- 当前导出使用最近一次已加载的摘要 latest[0]，然后附加 AuditLog.read；不是点击导出时重新完整采集。全局镜像还受 head -n 160 限制。
- FeatureSettings.diagnostic 将最近状态写入模块 Provider，失败时尝试 Settings.Global，同名键覆盖。
- AiTriggerSpeedHook.traceStage 在详细诊断启用时通过 Android Log.i 写 AI_STAGE：序列、wall/uptime、线程、阶段。当前导出未采集此类系统日志。
- 肩键相关 Hook 的部分接入、错误由模块日志接口输出，当前导出也没有合并完整的框架日志。
- AuditLog.write 的调用者主要为 RootHideManager 与 AugmentTileService：保存目标数量与移除系统目标；单应用 hide/unhide 结果、尝试次数或失败状态；全部隐藏/显示的成功及失败数量；磁贴动作结果。这不是所有功能的完整日常调用历史。
- 文件为模块私有 files/ls_augment.log；超过约 192 KiB 时缩至约 96 KiB，不按天保存。现有 compact 只读取开头最多 192 KiB，边界处可能丢失超出部分的新记录，后续模块实现需修正保留最新完整行。

## 用户要求与验收标准

1. 页面只保留“日志”和“导出日志”。导出为一个用于排查问题的文件；用户无需手动分别收集日志。
2. 导出时重新采集设备、ROM、Android、模块、LSPosed、目标应用版本，配置状态及采集时间。避免旧摘要和新日志混合无说明。
3. 每个目标进程报告包名、PID、启动时间、模块加载状态、Hook 目标类/方法及注册结果、最后命中、调用次数与最近错误。区分“未知/无权限/未采集”“未触发”“安装失败”；不能把 Hook 注册成功等同于功能生效。
4. 开启肩键详细诊断时，包含本次复现的按下、派发、连点间隔、松开停止、兼容性、原生调用和熔断/异常记录。
5. 开启 AI 详细诊断时，包含扫描、识别、复核、队列、实际点击或取消、耗时及错误。按关联 ID、进程、线程、时间戳关联同一次调用。
6. 合并对应功能的模块状态记录、受限的系统日志和可获取的 LSPosed 相关日志。只收集目标标签、目标进程与复现时段，不无差别导出其它应用的日志。
7. 文件明确列出每项日志来源、实际采集起止时间、条数、截断/轮转情况、采集失败原因。没有读取权限时写清缺失信息，不能伪装完整成功。
8. 提示使用步骤：开启详细诊断 → 重启相关作用域 → 复现问题 → 导出。开启之前的调用无法补录；不能用旧进程、旧模块版本记录证明本次生效。
9. 日常保留低频的重要状态变化、失败和用户操作结果；详细高频调用只在对应诊断开启时记录。采用有限大小的滚动保留与重复记录限频，导出不修改业务配置。
10. 实机验收覆盖：两项详细诊断关闭、各单独开启、同时开启、未复现、Hook 安装失败、已接入但未命中、已命中但执行失败、日志截断、权限不足及重启后旧记录混入。

## 网页已落实

日志按钮按当前两项详细诊断开关生成单个 TXT 结构示例；包含基础字段和所选详细阶段。文件全篇明确模拟、未采集真实设备，不对真实 Hook 成功做结论。

## 日常日志建议

保留低频、有限体积的基础日志，有助于追查误隐藏、恢复失败和磁贴操作；不需要常驻记录每次扫描或点击。详细诊断承担复现期间的调用分析，日常日志承担事件追溯。
